# Deploy — S3 + CloudFront

**When to pick this:** the subject is already on AWS, or the site has to live where the rest of their infrastructure does.

---

## Prerequisites

| Need | Check |
|---|---|
| AWS CLI v2 | `aws --version` |
| Credentials configured | `aws sts get-caller-identity` |
| A bucket | `aws s3 ls s3://<bucket>` |
| A CloudFront distribution | `aws cloudfront get-distribution --id <dist-id>` |
| A built site directory | `ls dist/index.html` |

Credentials come from a named profile, SSO, or an instance role. Never an access
key in a file inside the repository, never one echoed into the transcript
(`§15`).

```bash
export AWS_PROFILE=<profile>
BUCKET=<bucket>
DIST=<distribution-id>
```

**Origin access.** Use Origin Access Control with a private bucket. The bucket
stays blocked from public access and only CloudFront can read it. Public-read
bucket policy plus S3 website endpoint still works and is the older answer; it
exposes the origin directly, bypasses CloudFront, and cannot serve https on the
S3 endpoint. Pick OAC.

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "cloudfront.amazonaws.com" },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::<bucket>/*",
    "Condition": { "StringEquals": {
      "AWS:SourceArn": "arn:aws:cloudfront::<account-id>:distribution/<dist-id>"
    }}
  }]
}
```

Default root object `index.html` on the distribution. A custom error response
maps 403 and 404 to `/404.html` with response code 404, since a private bucket
returns 403 for a missing key.

## Snapshot

**Hard rule (`§15`). No snapshot, no deploy.** Turn on bucket versioning first,
so every overwrite is recoverable at the object level.

```bash
aws s3api put-bucket-versioning --bucket $BUCKET \
  --versioning-configuration Status=Enabled

mkdir -p runs/<slug>/snapshot
aws s3 sync s3://$BUCKET/ runs/<slug>/snapshot/site/ --quiet

aws s3api list-object-versions --bucket $BUCKET \
  > runs/<slug>/snapshot/object-versions.json
aws cloudfront get-distribution-config --id $DIST \
  > runs/<slug>/snapshot/distribution-config.json

date -u +%Y-%m-%dT%H:%M:%SZ > runs/<slug>/rollback-ref.txt
```

The timestamp is the rollback reference: with versioning on, it identifies
which object versions were current. Keep the local sync as well, because a
lifecycle rule that expires noncurrent versions will eventually eat the other
option.

## Deploy

Two passes, because cache headers differ by file type and one blanket policy is
wrong for both halves.

```bash
# 1. Hashed assets. Immutable, cached for a year.
aws s3 sync dist/ s3://$BUCKET/ --delete \
  --exclude '*' --include 'assets/*' \
  --cache-control 'public, max-age=31536000, immutable'

# 2. Everything else. Revalidated every request.
aws s3 sync dist/ s3://$BUCKET/ --delete \
  --exclude 'assets/*' \
  --cache-control 'public, max-age=0, must-revalidate'
```

Content types S3 guesses wrong, set explicitly:

```bash
aws s3 cp dist/ s3://$BUCKET/ --recursive \
  --exclude '*' --include '*.woff2' \
  --content-type 'font/woff2' \
  --cache-control 'public, max-age=31536000, immutable' \
  --metadata-directive REPLACE
```

Then invalidate. Nothing is live until this finishes.

```bash
INVAL=$(aws cloudfront create-invalidation --distribution-id $DIST \
        --paths '/*' --query 'Invalidation.Id' --output text)
aws cloudfront wait invalidation-completed --distribution-id $DIST --id $INVAL
curl -sI https://<domain>/ | head -1
```

Verify with eyes, not a status code (`§14`).

## Rollback

```bash
aws s3 sync runs/<slug>/snapshot/site/ s3://$BUCKET/ --delete
aws cloudfront create-invalidation --distribution-id $DIST --paths '/*'
```

Version-level restore, when the local snapshot is gone and versioning was on:

```bash
aws s3api list-object-versions --bucket $BUCKET --prefix index.html \
  --query 'Versions[?IsLatest==`false`] | [0].VersionId' --output text
aws s3api copy-object --bucket $BUCKET --key index.html \
  --copy-source "$BUCKET/index.html?versionId=<version-id>"
```

The re-sync is the one to reach for at a bad moment. It is one command, it
restores the whole tree, and it does not require reasoning about version ids
per object. Always follow it with an invalidation; without one, the CDN keeps
serving the broken deploy for as long as its TTL says.

## Domain and TLS

**The certificate must be in `us-east-1`.** CloudFront reads ACM only from
North Virginia, whatever region the bucket is in. A certificate issued in
`eu-central-1` will not appear in the distribution's dropdown and the failure
gives no useful message.

```bash
aws acm request-certificate --region us-east-1 \
  --domain-name <domain> --subject-alternative-names www.<domain> \
  --validation-method DNS
aws acm describe-certificate --region us-east-1 --certificate-arn <arn> \
  --query 'Certificate.DomainValidationOptions[].ResourceRecord'
```

Create the returned CNAME validation records, wait for `ISSUED`, then attach the
certificate and set both hostnames as distribution aliases.

Route 53:

```
<domain>       A  ALIAS -> <dist-id>.cloudfront.net.
www.<domain>   A  ALIAS -> <dist-id>.cloudfront.net.
```

External DNS: `CNAME` for `www`, and an `ALIAS`/`ANAME` for the apex if the
registrar supports it.

Set the distribution's viewer protocol policy to `redirect-to-https`. Redirect
one hostname to the other with a CloudFront Function so both are deliberate.

```bash
curl -sI http://<domain>/ | grep -i '^location'
curl -sI https://www.<domain>/ | head -1
```

## Forms and conversion

Nothing here handles a POST. Per `loops/05-share.md`, the options are `mailto:`,
Formspree, Tally, or a link out.

The AWS-native path is API Gateway plus a Lambda that calls SES, wired as a
second CloudFront origin on `/api/*` so there is no CORS preflight. It is a real
option and it is three more services to own, monitor, and pay for, for one
contact form. Take it when the rest of the subject's stack already lives on AWS.

| Path | Cost | Note |
|---|---|---|
| `mailto:` or link out | none | Correct default here |
| Formspree / Tally | free tier | Third-party POST endpoint, honeypot field |
| API Gateway + Lambda + SES | cents | SES starts sandboxed, and the recipient must be verified before anything is delivered |

Whichever it is, submit it end to end from the live domain and confirm arrival
before Gate C.

## Gotchas

- **ACM in the wrong region.** The single most common failure on this target.
  `us-east-1`, always, no matter where the bucket lives.
- **Forgetting the invalidation.** The sync succeeds, the site looks unchanged,
  and an hour goes into debugging a deploy that already worked.
- **Invalidation is not free at volume.** First 1,000 paths per month are free,
  then it is per path. `/*` counts as one path, which is why it is used above.
- **`--delete` deletes.** Pointed at the wrong local directory it empties the
  bucket. Versioning turns that from a disaster into an afternoon, which is the
  real reason to enable it before the first deploy.
- **Missing `--content-type`.** S3 stores unknown extensions as
  `application/octet-stream`, and the browser downloads the font instead of
  rendering the page. Check with `curl -sI https://<domain>/assets/x.woff2`.
- **Trailing-slash URLs 404.** CloudFront's default root object applies only to
  the root. `/projects/` needs a CloudFront Function rewriting `/$` to
  `/index.html`, or every directory-style URL breaks.
- **A public bucket with a website endpoint is still reachable.** It serves the
  same content over plain http, outside the CDN, with no headers. Another reason
  for OAC and a blocked bucket.
